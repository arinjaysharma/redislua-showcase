Lua Script — executed atomically
-- KEYS[1] : sorted-set per client IP
-- ARGV    : now_ms, window_ms, limit, uid

local now    = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit  = tonumber(ARGV[3])

-- Evict expired entries
redis.call('ZREMRANGEBYSCORE',
  KEYS[1], '-inf', now - window)

local count = redis.call('ZCARD', KEYS[1])

if count < limit then
  redis.call('ZADD', KEYS[1], now, ARGV[4])
  redis.call('PEXPIRE', KEYS[1], window)
  return {1, limit - count - 1, now + window}
else
  local oldest = redis.call(
    'ZRANGE', KEYS[1], 0, 0, 'WITHSCORES')
  return {0, 0, tonumber(oldest[2]) + window}
end
Why Lua? A naive GET → compare → INCR has a race window between reads. Lua collapses the entire sliding-window check into one uninterruptible Redis command.

Why Lua? A plain DEL would release any holder's lock. The Lua script atomically verifies the token before deleting — making crash-safe ownership checking possible.

-- KEYS[1] : leaderboard sorted set
-- ARGV    : player, score, topN, range

redis.call('ZADD', KEYS[1],
  tonumber(ARGV[2]), ARGV[1])

-- Rank is now consistent with
-- the ZADD above — same snapshot
local rank = redis.call(
  'ZREVRANK', KEYS[1], ARGV[1])

local topList = redis.call(
  'ZREVRANGE', KEYS[1],
  0, ARGV[3]-1, 'WITHSCORES')

local nb = redis.call('ZREVRANGE',
  KEYS[1],
  math.max(0, rank-ARGV[4]),
  rank + ARGV[4], 'WITHSCORES')

local total = redis.call(
  'ZCARD', KEYS[1])

return {rank+1, score, total,
        topList, nb}
Why Lua? Between two separate ZREVRANK calls another write could shift ranks. Lua freezes the view: score update + rank + neighbors are all read from the same consistent snapshot.

Lua Script — atomic guard
-- KEYS[1] : stock counter
-- ARGV[1] : quantity

local qty   = tonumber(ARGV[1])
local stock = redis.call('GET', KEYS[1])

if stock == false then
  return {-2, 0} -- not init
end

stock = tonumber(stock)

-- The guard: check AND decrement
-- happen atomically. 1000 concurrent
-- goroutines cannot all pass this if.
if stock < qty then
  return {-1, stock} -- no stock
end

local rem = tonumber(
  redis.call('DECRBY', KEYS[1], qty))

return {rem, rem}
Why Lua? GET → if → DECRBY in Go has a race: 1000 goroutines all read stock=1 and all decrement. Lua collapses check+decrement into one uninterruptible step.

Lua Script — atomic transfer
-- KEYS[1] sender  KEYS[2] receiver
-- KEYS[3] txn log
-- ARGV[1] amount  ARGV[2] txn_id

local from_bal = tonumber(
  redis.call('GET', KEYS[1]) or '0')

-- Guard: reject if insufficient
if from_bal < tonumber(ARGV[1]) then
  return {-1, from_bal, 0}
end

-- Atomic debit + credit
local new_from = tonumber(
  redis.call('DECRBY', KEYS[1], ARGV[1]))
local new_to = tonumber(
  redis.call('INCRBY', KEYS[2], ARGV[1]))

-- Append to transaction log
redis.call('LPUSH', KEYS[3],
  ARGV[2]..'|'..ARGV[1]..'|'
  ..new_from..'|'..new_to)
redis.call('LTRIM', KEYS[3], 0, 49)

return {1, new_from, new_to}
Why Lua? A crash after DECRBY but before INCRBY destroys money. Lua's atomicity guarantees the transfer is all-or-nothing, plus the log write is included in the same atomic unit.
